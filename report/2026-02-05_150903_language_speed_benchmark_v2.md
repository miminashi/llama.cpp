# 言語速度比較ベンチマーク v2

日付: 2026-02-05 15:09

## 目的

前回の調査（2026-02-05_133246_language_speed_comparison.md）で観測されたクラスタ環境での速度バラツキを、llama-benchの複数回測定（-r 5）で定量化する。

## テスト環境

- **モデル**: gpt-oss-120b (Q4_K_M, 58.45 GiB, 116.83B params)
- **ローカル**: 7× Tesla P100-PCIE-16GB
- **クラスタ**: 7× ローカル P100 + 4× リモート P100 (RDMA経由)
- **GPUDirect RDMA**: 有効
- **測定方法**: llama-bench -r 5 (5回測定、平均±標準偏差を出力)
- **テストパラメータ**: pp128 (プロンプト128トークン), tg32 (生成32トークン)

## 結果

### ローカル 7GPU（ベースライン）

| テスト | 速度 (t/s) | 標準偏差 | 変動係数 (CV) |
|--------|:----------:|:--------:|:-------------:|
| pp128  | 213.85     | ± 5.30   | 2.5%          |
| tg32   | 43.63      | ± 0.24   | 0.5%          |

### クラスタ 11GPU (7 CUDA + 4 RDMA)

| テスト | 速度 (t/s) | 標準偏差 | 変動係数 (CV) |
|--------|:----------:|:--------:|:-------------:|
| pp128  | 46.12      | ± 16.26  | **35.3%**     |
| tg32   | 2.99       | ± 0.70   | **23.4%**     |

### 比較

| 指標 | ローカル 7GPU | クラスタ 11GPU | クラスタ/ローカル比 |
|------|:-------------:|:--------------:|:-------------------:|
| pp128 速度 | 213.85 t/s | 46.12 t/s | 21.6% |
| pp128 変動係数 | 2.5% | 35.3% | 14倍 |
| tg32 速度 | 43.63 t/s | 2.99 t/s | 6.9% |
| tg32 変動係数 | 0.5% | 23.4% | 47倍 |

## 分析

### 1. 速度低下の主因

クラスタ構成では大幅な速度低下が見られる：
- **pp128**: ローカルの21.6%（約4.6倍遅い）
- **tg32**: ローカルの6.9%（約14.6倍遅い）

これは以下の要因による：
1. **逐次実行によるオーバーヘッド**: 4台のRDMAデバイスが逐次的に`graph_compute`を呼び出す（各トークンで4回のラウンドトリップ）
2. **RDMA通信レイテンシ**: 各graph_computeでコマンド送信→計算→結果返送
3. **同期オーバーヘッド**: GPUDirect RDMAでもプロトコルの同期処理が必要

### 2. バラツキの要因

クラスタ環境での高い変動係数（CV）は言語とは無関係：
- **ローカル**: 非常に安定（CV 0.5-2.5%）
- **クラスタ**: 大きなバラツキ（CV 23-35%）

バラツキの原因として考えられる要因：
1. **ネットワーク状態の変動**: RDMA over Infinibandのレイテンシ変動
2. **サーバーGPU状態**: 前回のメモリ（MEMORY.md）で記録した「GPUコンピュート時間が2-3倍変動」現象
3. **バッファ状態**: ステージングバッファやIBキューの状態
4. **初回ウォームアップ効果**: 最初の数回が特に遅い可能性

### 3. 前回調査との整合性

前回（llama-cliでの手動測定）の結果：
- 日本語/英語で「速い回」「遅い回」が交互に出現
- 言語による有意差なし

今回の結果はこれを裏付ける：
- llama-bench（言語指定なし、ランダムトークン）でも同様のバラツキ
- **バラツキは言語ではなくクラスタ環境固有の現象**

## 結論

1. **言語による速度差はない** — 前回調査の結論を再確認
2. **クラスタでのバラツキは構造的な問題** — CV 23-35%は非常に大きい

## 改善の方向性（詳細分析）

### 1. RDMAデバイスの並列化

#### 現状の問題

現在の`ggml_backend_sched_compute_splits()`関数（ggml-backend.cpp:1443）は、各スプリット（バックエンド単位の計算グラフ）を**順番に処理**している：

```cpp
for (int split_id = 0; split_id < sched->n_splits; split_id++) {
    // 入力テンソルのコピー
    // ...
    enum ggml_status ec = ggml_backend_graph_compute_async(split_backend, &split->graph);
    // ここでブロック（レスポンス待ち）
}
```

11GPUクラスタ（7 CUDA + 4 RDMA）では、レイヤー分割により約8〜11のスプリットが生成される。各RDMAデバイスへの`graph_compute`呼び出しは**同期的**で、サーバーからのレスポンスを待ってから次のスプリットに進む。

#### 影響

- **tg32で特に深刻**: 生成フェーズでは各トークンごとに全スプリットを順番に実行
- 4つのRDMAデバイス = 4回のネットワークラウンドトリップ/トークン
- 仮に1回のラウンドトリップが5msなら、4デバイスで20ms/トークン → 最大50 t/s が上限

#### 改善案

**A. 非同期リクエスト + 一括待機**
```
現在:  send(RDMA0) → wait → send(RDMA1) → wait → send(RDMA2) → wait → send(RDMA3) → wait
改善:  send(RDMA0) → send(RDMA1) → send(RDMA2) → send(RDMA3) → wait_all
```

- 複数のRDMAデバイスに対して並列にリクエストを送信
- 全デバイスの完了を一括で待機
- レイテンシを「最大値」に削減（4回分→1回分）

**B. 実装の課題**
- `ggml_backend_sched`の設計変更が必要（llama.cpp本体への大きな変更）
- スプリット間のデータ依存性を解決する必要あり（前のスプリットの出力 → 次の入力）
- 同一ノード内のCUDAバックエンドとの同期も考慮必要

**C. 期待効果**
- 理論上、RDMAデバイス数に比例してtg速度が改善（4デバイス → 最大4倍）
- 実際にはデータ依存性により、並列化できる範囲は限定的

---

### 2. コマンドパイプライン化による同期オーバーヘッド削減

#### 現状の問題

現在のRDMAプロトコルは**リクエスト-レスポンス型**で、各コマンドが同期的に処理される：

```
クライアント                    サーバー
    |--- FLUSH_AND_COMPUTE --->|
    |                          | (GPU計算)
    |<------ response ---------|
    |--- 次のコマンド ---------->|
```

`graph_compute`1回あたりの内訳（プロファイリング結果より）：
- コマンド送信: ~0.1ms
- サーバー側GPU計算: ~2-10ms（変動大）
- レスポンス受信: ~0.1ms
- **合計: ~2-10ms/回**

#### 改善案

**A. コマンドパイプライン化**
```
現在:  cmd1 → rsp1 → cmd2 → rsp2 → cmd3 → rsp3
改善:  cmd1 → cmd2 → cmd3 → rsp1 → rsp2 → rsp3
```

- 複数のコマンドを連続送信し、レスポンスを後でまとめて受信
- ネットワークレイテンシを隠蔽

**B. Fire-and-Forget モード**
- 一部のコマンド（`set_tensor`のフラッシュなど）はレスポンス不要
- 現在の`FLUSH_AND_COMPUTE`統合は部分的にこれを実現済み
- さらに`GRAPH_COMPUTE`のレスポンスを非同期化できれば効果大

**C. 実装の課題**
- サーバー側で複数コマンドのキューイングが必要
- エラーハンドリングの複雑化（どのコマンドが失敗したか特定困難）
- 順序保証とデータ整合性の管理

**D. 期待効果**
- ネットワークRTT（往復遅延）を1回分に削減
- 特にコマンド数が多い場合に効果的（フル転送時など）

---

### 3. サーバー側のウォームアップ処理

#### 現状の問題

GPUは初回計算時に以下のオーバーヘッドが発生する：

1. **CUDAカーネルのJITコンパイル**: 初めて実行するカーネルはコンパイルが必要
2. **メモリアロケーション**: 初回のcudaMallocは遅い場合がある
3. **GPU周波数のスケーリング**: アイドル状態からの復帰時に低周波数で動作
4. **キャッシュの冷え**: L2キャッシュやTLBが空の状態

これらが最初の数回の`graph_compute`で顕著に現れ、バラツキの一因となっている可能性がある。

#### 現象の証拠

- llama-benchの5回測定で標準偏差が大きい（特にpp128で±16.26）
- MEMORY.mdに記録された「GPUコンピュート時間が2-3倍変動」
- 「速い回」「遅い回」が交互に出現する現象

#### 改善案

**A. サーバー起動時のウォームアップ**
```cpp
// rdma-server起動時
for (int device = 0; device < num_devices; device++) {
    // ダミーの計算グラフを作成・実行
    ggml_cgraph * warmup_graph = create_warmup_graph(device);
    ggml_backend_graph_compute(backends[device], warmup_graph);
}
```

- サーバー起動時に各GPUでダミー計算を実行
- カーネルコンパイルとメモリアロケーションを事前に完了

**B. 接続時のウォームアップ**
- クライアント接続時に、そのセッションで使用するグラフ構造に近いダミー計算を実行
- より効果的だが、グラフ構造の事前知識が必要

**C. GPU周波数の固定**
```bash
# nvidia-smiでGPU周波数を最大に固定
nvidia-smi -pm 1  # Persistence Mode有効化
nvidia-smi -lgc <max_freq>  # クロック固定
```

- アイドル時の周波数低下を防止
- 消費電力は増加するが、レイテンシは安定

**D. 期待効果**
- 初回実行時のレイテンシスパイクを排除
- バラツキ（CV）の低減
- ただし、平均速度への影響は限定的（初回のみの問題なので）

---

## 改善の優先順位

| 改善項目 | 実装難易度 | 期待効果 | 推奨優先度 |
|---------|:----------:|:--------:|:----------:|
| RDMAデバイス並列化 | 高 | 大（最大4倍） | 中期 |
| コマンドパイプライン化 | 中 | 中（20-30%改善） | 中期 |
| サーバーウォームアップ | 低 | 小（バラツキ低減） | **短期** |

**推奨アプローチ**:
1. まずサーバーウォームアップを実装（低コストで効果検証可能）
2. プロファイリングでボトルネックを特定
3. 並列化の設計検討（llama.cpp本体の変更が必要なため慎重に）
