# RDMAタイムアウト問題 修正レポート

- **実施日時**: 2026年2月3日 19:05

## 前提・目的

llama-cliでRDMAバックエンドを使用してモデルをロードする際にタイムアウトエラーが発生する問題を修正する。

- 背景: モデルロード中に「Send completion timeout」エラーが発生し、処理が中断される
- 目的: タイムアウトの原因を特定し、モデルロードを成功させる
- 前提条件: 1号機（192.168.100.1）と2号機（192.168.100.2）が100GbEで接続されていること

### 発生していたエラー

```
[rdma_connection] Send completion timeout
ggml-rdma.cpp:438: Remote RDMA server crashed or returned malformed response
```

## 根本原因の分析

調査の結果、以下の3つの問題を特定した：

### 1. タイムアウト値が短すぎる（5秒）
`rdma-transport.cpp`のsend/recv関数でwait_for_completionに渡されるタイムアウト値が5000ms（5秒）だった。モデルのinit_tensor処理が多数発生する場合、この値では不十分。

### 2. wait_for_completion()のpoll_cq()リトライ不足
CQ（Completion Queue）イベントを受信した後、poll_cq()でWC（Work Completion）が見つからない場合がある。元のコードでは一度だけのpoll_cq()試行で失敗扱いにしていた。

### 3. プロトコル同期の不一致（最重要）
サーバー側では全てのコマンドに対してrsp_size（応答サイズ、応答データがない場合は0）を送信していたが、クライアント側の`send_rdma_cmd`関数では応答データを期待しないコマンド（init_tensor等）でrsp_sizeを受信していなかった。

これにより、クライアントが次のコマンドを送信しようとした時に、サーバーからの前のrsp_sizeがまだ受信バッファにあり、プロトコルの同期がずれてタイムアウトが発生していた。

## 修正内容

### 修正ファイル

| ファイル | 変更内容 |
|---------|---------|
| `ggml/src/ggml-rdma/rdma-transport.cpp` | タイムアウト値増加、wait_for_completion改良 |
| `ggml/src/ggml-rdma/ggml-rdma.cpp` | プロトコル同期修正 |

### 1. タイムアウト値の増加 (rdma-transport.cpp)

```cpp
// 変更前
if (!wait_for_completion(5000)) {

// 変更後
if (!wait_for_completion(30000)) {
```

send()およびrecv()のタイムアウトを5秒から30秒に延長。

### 2. wait_for_completion()のリトライロジック追加 (rdma-transport.cpp)

```cpp
// Poll for completion with retry logic
// CQ event may arrive before WC is visible in poll_cq(), so retry multiple times
struct ibv_wc wc = {};
const int max_poll_retries = 100;
const int poll_retry_delay_us = 100; // 100 microseconds

for (int retry = 0; retry < max_poll_retries; retry++) {
    int n = ibv_poll_cq(cq_, 1, &wc);
    if (n < 0) {
        GGML_LOG_ERROR("[rdma_connection] Failed to poll CQ: %s\n", strerror(errno));
        return false;
    }
    if (n > 0) {
        if (wc.status != IBV_WC_SUCCESS) {
            GGML_LOG_ERROR("[rdma_connection] Work completion error: %s\n", ibv_wc_status_str(wc.status));
            return false;
        }
        return true;
    }
    // WC not yet available, wait briefly and retry
    usleep(poll_retry_delay_us);
}
```

CQイベント受信後、WCが見つからない場合は最大100回（計10ms）リトライする。

### 3. プロトコル同期の修正 (ggml-rdma.cpp)

```cpp
// Internal: send command and input data only (no response handling)
static bool send_rdma_cmd_raw(rdma_connection * conn, rdma_cmd cmd, const void * input, size_t input_size,
                              struct ibv_mr * send_mr) {
    // コマンドと入力データのみ送信
    ...
}

// Send command with no response data expected (server still sends rsp_size=0)
static bool send_rdma_cmd(rdma_connection * conn, rdma_cmd cmd, const void * input, size_t input_size,
                          struct ibv_mr * send_mr) {
    if (!send_rdma_cmd_raw(conn, cmd, input, input_size, send_mr)) {
        return false;
    }

    // Server always sends rsp_size (8 bytes), even for commands with no response data.
    // We must receive it to keep the protocol synchronized.
    uint64_t rsp_size = 0;
    if (!conn->recv(&rsp_size, sizeof(rsp_size), nullptr)) {
        return false;
    }
    ...
}

static bool send_rdma_cmd_with_rsp(rdma_connection * conn, rdma_cmd cmd,
                                    const void * input, size_t input_size,
                                    void * output, size_t output_size) {
    if (!send_rdma_cmd_raw(conn, cmd, input, input_size, nullptr)) {
        return false;
    }
    return recv_rdma_rsp(conn, output, output_size, nullptr);
}
```

- `send_rdma_cmd_raw`: コマンドと入力データのみを送信（応答処理なし）
- `send_rdma_cmd`: 応答データなしコマンド用（サーバーからのrsp_size=0を受信）
- `send_rdma_cmd_with_rsp`: 応答データありコマンド用（rsp_sizeとデータを受信）

## 残存する問題

推論（グラフ計算）フェーズで新たなエラーが発生：

```
[rdma_connection] Message too large for inline send without MR
[rdma_connection]   size=387900, max_inline=256, send_buffer_.size()=65536, send_mr_=...
```

これはグラフ計算時に送信されるメッセージサイズ（387900バイト）が内部送信バッファサイズ（65536バイト）を超えているため。これは本修正の範囲外であり、別途対応が必要。

## 結論

RDMAプロトコルの同期問題を修正し、モデルロード時のタイムアウトエラーを解消した。タイムアウト値の延長とpoll_cq()のリトライロジック追加も安定性向上に寄与している。
