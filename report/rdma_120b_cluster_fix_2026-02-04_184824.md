# RDMA 120b クラスタ修正レポート — supports_buft クロスデバイスバグ修正

- **実施日時**: 2026年2月4日 18:48
- **参照レポート**: [rdma_benchmark_gpt_oss_2026-02-04_110225.md](rdma_benchmark_gpt_oss_2026-02-04_110225.md)

## 前提・目的

### 背景
前回のベンチマークレポートでは、gpt-oss-20b/120b を 11GPU クラスタ（1号機 7×P100 + 2号機 4×P100、100GbE RoCE v2接続）で動作させた際、**複数 RDMA デバイス使用時に `CUDA error: an illegal memory access was encountered` が発生**し、推論が完了しなかった。

1 RDMA デバイスのみでは正常動作するが、4 RDMA デバイス使用時にクラッシュする問題。

### 目的
1. 1号機と2号機のコードベースを同期する
2. 120b クラスタテスト（CUDA+RDMA混在）の `illegal memory access` エラーを解決する
3. 修正後にベンチマークを再実行する

### 前提条件
- 1号機: 7×Tesla P100-PCIE-16GB (192.168.100.1)
- 2号機: 4×Tesla P100-PCIE-16GB (192.168.100.2)、rdma-server として動作
- 100GbE RoCE v2 接続
- GPUDirect RDMA: 無効 (`GGML_RDMA_NO_GDR=1`)
- モデル: gpt-oss-20b-Q4_K_M、gpt-oss-120b-Q4_K_M（共に MoE アーキテクチャ）

## 原因分析

### エラー症状
```
CUDA error: an illegal memory access was encountered
  current device: 0, in function ggml_cuda_mul_mat_id at ggml-cuda.cu:2328
  cudaMemcpyAsync(ids_host.data(), ids->data, ggml_nbytes(ids), cudaMemcpyDeviceToHost, stream)
```

### 調査過程

#### 仮説 1: ibv_reg_mr による CUDA メモリ破壊 → **棄却**
`GGML_RDMA_NO_GDR=1` をサーバー側にも設定し MR 登録を完全にスキップしても、同じエラーが発生。

#### 仮説 2: クロスデバイステンソルアクセス → **部分的に正しい**
1 RDMA デバイスでは動作するが 4 RDMA デバイスでは失敗することから、クロスデバイスアクセスを疑った。サーバー側でデバッグログを追加し、デバイス 0 のグラフに **デバイス 1, 2, 3 のテンソル 117 個** が参照されていることを確認。

サーバー側でクロスデバイスコピー（D2H + H2D）を実装するも、依然としてクラッシュ。

#### 根本原因: `supports_buft` の不正な実装 → **確定**

`ggml_backend_rdma_device_supports_buft()` の実装:
```cpp
// 修正前（バグ）
return strstr(name, ctx->endpoint.c_str()) != nullptr;
```

バッファタイプ名は `"RDMA0[192.168.100.2:50051]"`, `"RDMA1[192.168.100.2:50051]"` 等。全 RDMA デバイスが同じエンドポイントを共有しているため、**RDMA0 が RDMA3 のバッファを「サポートしている」と誤って宣言**していた。

これにより `ggml_backend_sched` は：
1. RDMA デバイス間のデータコピーが不要と判断
2. 全 RDMA レイヤーを 1 つのデバイス（RDMA0）のグラフに含める
3. サーバー側でデバイス 0 の CUDA バックエンドが、デバイス 1/2/3 のメモリを参照して `illegal memory access`

### 修正内容

`ggml-rdma.cpp` の `ggml_backend_rdma_device_supports_buft()`:
```cpp
// 修正後
return strcmp(name, ctx->name.c_str()) == 0;
```

各 RDMA デバイスは **自分自身のバッファタイプのみ** サポートすると宣言。これにより `ggml_backend_sched` が正しくデバイス間コピーを挿入し、各デバイスのグラフは自身のテンソルのみ参照するようになった。

### 追加修正

1. **チャンク送受信** (`rdma-transport.cpp`): 141MB の MoE エキスパート重みが 16MB 内部バッファを超過する問題を修正。自動チャンク分割を実装。

2. **クロスデバイスコピー安全ネット** (`ggml-rdma.cpp`): サーバー側の `graph_compute`, `graph_recompute`, `graph_compute_update` にクロスデバイスコピーヘルパー関数を追加。`stored_graph` にアロケーション追跡を追加しダングリングポインタを防止。

3. **`stored_graph` 構造体の強化**: クロスデバイスアロケーションのライフサイクル管理を追加。

```bash
GGML_RDMA_NO_GDR=1 LD_LIBRARY_PATH=/home/ubuntu/projects/llama.cpp/build/bin \
  /home/ubuntu/projects/llama.cpp/build/bin/rdma-server -H 0.0.0.0 -p 50051
```

### 1号機でテストを実行
```bash
GGML_RDMA_SERVERS=192.168.100.2:50051 \
GGML_RDMA_NO_GDR=1 \
LD_LIBRARY_PATH=/home/ubuntu/projects/llama.cpp/.worktree/rdma-backend/build/bin \
  /home/ubuntu/projects/llama.cpp/.worktree/rdma-backend/build/bin/llama-cli \
  -hf unsloth/gpt-oss-120b-GGUF:Q4_K_M \
  -dev 'CUDA0,CUDA1,CUDA2,CUDA3,CUDA4,CUDA5,CUDA6,RDMA0[192.168.100.2:50051],RDMA1[192.168.100.2:50051],RDMA2[192.168.100.2:50051],RDMA3[192.168.100.2:50051]' \
  -sm layer -ngl 999 -c 2048 -p 'こんにちは' -n 50 \
  --no-warmup --single-turn --simple-io
```

## まとめ

- `supports_buft` の1行修正（`strstr` → `strcmp`）により、`ggml_backend_sched` が正しくRDMAデバイス間のグラフ分割を行うようになった
- 20b/120b 両モデルで 11GPU クラスタ（7 CUDA + 4 RDMA）による推論が安定動作
- 120b モデルは約 60GB のメモリを 11 GPU に分散配置し、Prompt 3-11 t/s、Generation 0.7-1.1 t/s で動作
