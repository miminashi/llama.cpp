# n_ubatch チューニング ベンチマーク

- **実施日時**: 2026年3月2日 20:59
- **ワークツリー**: なし (`feature/rdma-backend` 直接)

## 前提・目的

`n_ubatch` (`-ub`) はプロンプトをサブバッチに分割するサイズで、デフォルト 512。異なる値で Prompt 処理 (pp) スループットがどう変わるかを測定する。

- **背景**: 非RDMA PP最適化調査 ([report/2026-03-02_200704_non_rdma_pp_optimization_survey.md](2026-03-02_200704_non_rdma_pp_optimization_survey.md)) で特定した6候補のうち、コード変更不要で即座に検証可能な候補
- **目的**: `-ub` 値が PP/TG スループットに与える影響を定量化し、最適値を特定する
- **仮説**: ub が小さいほど graph_compute の呼出回数が増え、オーバーヘッド (graph build, RDMA flush) が蓄積する。逆に ub が大きいほどバッチあたりの計算量が増え、GPU 利用効率が向上する

## テスト構成

| 項目 | 値 |
|------|-----|
| モデル | Qwen3.5-35B-A3B UD-Q4_K_M (MoE, 3B active) |
| GPU 構成 | Node 1 CUDA5,6 + Node 2 RDMA0-3 (6GPU) |
| ツール | llama-cli (llama-bench は Qwen3.5 MoE で OOM) |
| 固定パラメータ | `-sm layer -ngl 999 -fa 1 -n 32 --no-warmup --single-turn --simple-io` |
| プロンプト | `/tmp/long_prompt.txt` (1098 words, ~1000+ tokens) |

## テスト条件

| 条件 | `-ub` 値 | 期待 ubatch 分割回数 |
|------|---------|-------------------------------|
| A | 64 | ~16 |
| B | 128 | ~8 |
| C | 256 | ~4 |
| D | 512 (デフォルト) | ~2 |
| E (追加) | 1024 | 1 (分割なし) |

各条件3回ずつ実行 (合計15回)。

## 再現方法

1. プロンプトファイル生成 (~1098 words のテキストを `/tmp/long_prompt.txt` に作成)

2. 各条件で llama-cli を実行:
   ```bash
   gpu-lock.sh run CUDA_VISIBLE_DEVICES=5,6 GGML_RDMA_SERVERS=192.168.100.2:50051 \
     build/bin/llama-cli \
     -hf unsloth/Qwen3.5-35B-A3B-GGUF:UD-Q4_K_M \
     -dev 'CUDA0,CUDA1,RDMA0[192.168.100.2:50051],RDMA1[192.168.100.2:50051],RDMA2[192.168.100.2:50051],RDMA3[192.168.100.2:50051]' \
     -sm layer -ngl 999 -fa 1 -ub <VALUE> \
     -f /tmp/long_prompt.txt -n 32 \
     --no-warmup --single-turn --simple-io --log-file /tmp/llama-cli.log 2>&1
   ```

3. 出力末尾の `[ Prompt: X t/s | Generation: Y t/s ]` から値を抽出

## 分析

### PP (Prompt 処理) への影響

**ub 値は PP スループットに極めて大きな影響を与える。**

- ub=64 → ub=512 で **+57.7%** の改善 (126.7 → 199.8 t/s)
- ub=512 → ub=1024 では **+1.4%** のみ — ub=512 が実質的な最適値
- ub を2倍にするごとに 12-19% の改善があるが、512→1024 で収束

**メカニズム**: ub が小さいほど `graph_compute` の呼出回数が増加し、graph build + RDMA flush 同期のオーバーヘッドが蓄積する。PP プロファイリング ([report/2026-03-02_195335_pp_profiling_qwen35_optimization.md](2026-03-02_195335_pp_profiling_qwen35_optimization.md)) で確認された通り、Qwen3.5 では FULL_GRAPH パスの flush 待ち (94.8%) が支配的であり、ub が小さいほどこの同期回数が増える。

ub=1024 (分割なし) でもほぼ改善がないのは、pp≈1000 tokens では ub=512 でも分割回数が2回程度と少なく、オーバーヘッドが十分に小さいため。

### TG (生成) への影響

**ub 値は TG スループットにほぼ影響しない** (全条件で 28.7-29.7 t/s の範囲内)。

これは期待通りの結果。TG はトークンを1つずつ生成するため、ubatch サイズは関係しない。

### デフォルト値 (ub=512) の妥当性

デフォルト値 512 は Qwen3.5 6GPU 構成において実質的な最適値。ub=1024 との差は +1.4% (統計的に有意とは言えない) であり、ub を 512 から増やしても実用的な改善は得られない。

## 結論

1. **ub=512 (デフォルト) が最適** — ub を下げると PP が大幅に劣化 (ub=64 で -36.6%)、ub を上げても改善はわずか (+1.4%)
2. **TG には影響なし** — ub 値に関わらず ~29 t/s で安定
3. **コード変更不要の最適化としては効果なし** — デフォルト値が既に最適であるため、ub チューニングによる PP 改善は期待できない
4. **注意**: ub を意図的に下げると大幅な性能劣化を引き起こすため、`-ub` のデフォルト値を変更すべきではない
