# GPU組み合わせベンチマーク性能ばらつき分析

## 日時
2026-02-05 19:20

## 問題の概要

GPU組み合わせベンチマーク (2026-02-05_170441) で報告された大きな性能ばらつき:
- RDMA 1+2: pp128 = 270.98 ± 185 t/s (標準偏差68%)
- RDMA 1+4: pp128 = 155.95 ± 187 t/s (標準偏差120%)

一方、GPUトポロジベンチマーク (2026-02-05_175811) では:
- GPU位置による性能差は最大4%のみ
- 標準偏差は小さい（安定）

## 調査結果

### 根本原因の特定

**約2秒のスパイク**がgraph_compute中にランダムに発生しており、これが標準偏差を大きくしている主因。

プロファイル分析結果:
```
[client profile] graph_compute #1: 2094.82 ms (reuse=0)
[client profile] graph_compute #2: 1894.81 ms (reuse=1) ← スパイク
[client profile] graph_compute #3: 1957.31 ms (reuse=1) ← スパイク
[client profile] graph_compute #4: 136.82 ms (reuse=1)  ← 正常
```

### スパイクの特性

1. **発生タイミング**: テスト境界（pp128/tg32の切り替え時）に集中
2. **持続時間**: 約1.9〜2.0秒（固定的）
3. **影響範囲**: pp128フェーズで頻発、tg32フェーズでは安定
4. **根本位置**: `send_cmd` 関数内（サーバー応答待ち）

### サーバーログ分析

```
[server profile] cmd FLUSH_AND_RECOMPUTE: total=2085.73 ms (recv=1957.48, rsp_send=0.01)
```

- `recv=1957.48ms`: サーバーがクライアントからのコマンドを約2秒待っている
- サーバー自体の処理 (compute) は常に8〜9msで安定
- **クライアント側の送信遅延**が原因

### 比較実験結果

| 構成 | pp128 安定性 | tg32 安定性 |
|------|:-----------:|:----------:|
| ローカル 2GPU | 328〜331 t/s (< 1%) | 63.6 t/s (< 0.1%) |
| RPC 1+1 | 271〜288 t/s (< 7%) | 45.5〜47.5 t/s (< 5%) |
| RDMA 1+1 | 24〜343 t/s (1400%差!) | 4.5〜56 t/s (1200%差!) |

**結論**: 問題はRDMA実装特有

### RoCE環境の確認

```
Infiniband device 'mlx5_0' port 1 status:
  link_layer: Ethernet  ← RoCE (RDMA over Converged Ethernet)
  rate: 100 Gb/sec (4X EDR)
```

エラーカウンタはすべて0、リンクレベルの問題なし。

### 長時間実行テスト (r=10)

```
pp128: 299.47 ± 164.89 t/s (大きなばらつき)
tg32:  59.22 ± 0.42 t/s  (非常に安定！)
```

- pp128フェーズ(#1〜#11)でスパイク多発
- tg32フェーズ(#12〜#330)ではスパイクなし、全て8〜9ms

## 推定原因

### 主仮説: テスト境界でのメモリ/バッファ再初期化

llama-benchがテスト間で `llama_memory_clear` や `llama_free` を呼び出す際に:
1. RDMA接続のバッファ状態がリセット
2. 次のgraph_computeで再登録/再送信が発生
3. この再初期化に約2秒かかる

### 副仮説: RoCEの輻輳制御/フロー制御

RoCE v2の再送タイムアウトやPFCの問題により、特定の条件下で約2秒の遅延が発生する可能性。ただし、エラーカウンタが0のため可能性は低い。

## 推奨される測定方法

1. **pp128とtg32を分離測定**
   - 各テストタイプを別々のllama-benchプロセスで実行
   - スパイクの影響を分離

2. **初回計測を除外**
   - ウォームアップ後の最初の1〜2回を統計から除外
   - または、同一接続で多数回（r=10以上）実行して平均化

3. **サーバー再起動なし連続実行**
   - サーバーを再起動せずに複数回テスト
   - 初期化コストを償却

## 今後の調査項目

1. `llama_memory_clear` がRDMAバックエンドに与える影響
2. テスト境界でのグラフキャッシュ無効化の挙動
3. RoCE輻輳制御設定の最適化
