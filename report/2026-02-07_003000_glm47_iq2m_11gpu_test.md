# GLM-4.7 IQ2_M 11GPUクラスタ動作テストレポート

- **実施日時**: 2026年2月7日 00:30

## 前提・目的

Step 5 (最終Step: GLM4.7 Q4 on 16 P100s) の事前検証として、GLM-4.7 IQ2_M を11GPUクラスタ (7 CUDA + 4 RDMA) で動作させ、性能と出力品質を確認する。

- **背景**: Step 4 (GPUDirect RDMA) 完了後、最終目標であるGLM-4.7の分散推論に向けた事前検証が必要
- **目的**: GLM-4.7 が 11GPU で動作するか確認し、pp/tg 性能を計測する
- **前提条件**: 1号機 (7×P100) と 2号機 (4×P100) が InfiniBand で接続済み、RDMAバックエンドが動作していること
- **参考レポート**: [2026-02-06_213701_rdma_optimization_benchmark.md](2026-02-06_213701_rdma_optimization_benchmark.md)

## 出力品質

**IQ2_M (2.7 bpw) では出力品質に重大な問題がある。**

GLM-4.7 は thinking model で `[Start thinking]` ~ `[End thinking]` 間に推論過程を出力するが、IQ2_M ではこの部分が完全にゴミ文字列になった:

```
[Start thinking]
E+,,0@D!4CE.-"$!+*:7#=(91*847,H844D)":<E5023C0B4F+B2#%25&.)$--(5DA"7C'62<016.9$<EF/E+*!H)(1@.*(4..@3
```

200トークン生成しても thinking のゴミ出力だけで実際の回答は生成されなかった。

**結論**: IQ2_M は GLM-4.7 にとって量子化が過剰であり、実用不可。

## 発見されたバグ

### 1. mmap + RDMA Write のアドレスオーバーフロー

llama-cli で `--no-mmap` を付けないと、`set_tensor` での RDMA Write がリモート MR 範囲を超えるアドレスに書き込もうとして `remote access error` が発生する。

```
[rdma_connection] Work completion error: status=remote access error, opcode=0, vendor_err=0x88
[rdma_connection] RDMA write completion timeout: size=363724800, remote_addr=0x76bbb40e3400, rkey=0x17b8a8
```

- **原因推定**: mmap ロードパス (`load_all_data` のオフセット +0x4f3) で `set_tensor` に渡される offset が、ステージングバッファのサイズを超えている
- **回避策**: `--no-mmap` フラグを使用
- **影響範囲**: llama-cli のみ (llama-bench は non-mmap パスを使用するため問題なし)

### 2. GPUDirect RDMA の RDMA Write タイムアウト

`GGML_RDMA_NO_GDR=1` を外して GPUDirect RDMA を有効化すると、20KB 程度の小さな RDMA Write でも 30秒タイムアウトする。

```
[rdma_connection] Completion timeout after 30000 ms
[rdma_connection] RDMA write completion timeout: size=20480, remote_addr=0x71a710000000, rkey=0x1fcc93
```

- **原因推定**: GPUDirect RDMA (nvidia-peermem) のサーバー側バッファ登録に問題がある可能性。gpt-oss-20b (Step 4) で確認した GPUDirect は動作していたが、GLM-4.7 のバッファサイズ (~10GB/GPU) で問題が顕在化した可能性
- **回避策**: `GGML_RDMA_NO_GDR=1` で CPU staging に切り替え
- **影響**: pp128 が大幅に低下 (Step 4 の結果では GPUDirect で 6.6 倍の差)

## Step 5 に向けた所見

### 量子化レベルの選択

IQ2_M (2.7 bpw, 114GB) は出力品質が使い物にならない。Step 5 で GLM-4.7 を実用的に動作させるには、より高品質な量子化が必要:

| 量子化 | bpw | 推定サイズ | 16GPU (256GB) | 11GPU (176GB) |
|--------|----:|----------:|:-------------:|:-------------:|
| IQ2_M | 2.7 | 114 GB | 収容可能 | 収容可能 (**品質×**) |
| Q3_K_M | ~3.5 | ~150 GB | 収容可能 | 収容不可 |
| IQ3_M | ~3.4 | ~145 GB | 収容可能 | 収容不可 |
| Q4_K_M | ~4.5 | ~195 GB | 収容可能 | 収容不可 |

**推奨**: Q3_K_M または IQ3_M (150GB前後) を16GPUで試行。Q4_K_M (195GB) は16GPU (256GB) でギリギリ。

### バグ修正の優先度

1. **mmap + RDMA Write バグ** (高): llama-cli での使用に影響。`--no-mmap` で回避可能だが根本修正が望ましい
2. **GPUDirect RDMA タイムアウト** (中): CPU staging で動作するが、pp性能に大きく影響。16GPUではさらに影響が大きい

### 性能見込み (16GPU)

- tg32: 7.66 t/s (11GPU) → RDMA GPU が4→8に増えるためリモート分の逐次処理増で若干低下の可能性
- pp128: 23.48 t/s (11GPU, CPU staging) → GPUDirect 修正後は大幅改善が期待できる
- MoE モデルは活性化パラメータが少ないため (355B中32B活性)、tg は比較的高速
