# GPU組み合わせベンチマーク

- **実施日時**: 2026年2月5日 17:04

## 前提・目的

様々なGPU組み合わせでのRDMA/RPC性能特性を把握する。前回のRDMA vs RPCベンチマーク (1+1, 7+4 GPU) を拡張し、ローカル/リモート比率の影響を分析する。

- **背景**: 前回テストでは1+1と7+4のみ測定
- **目的**: GPU組み合わせごとの性能特性を定量化
- **前提条件**:
  - 1号機 (192.168.100.1): 7× Tesla P100-PCIE-16GB
  - 2号機 (192.168.100.2): 4× Tesla P100-PCIE-16GB
  - InfiniBand 100Gbps (Mellanox ConnectX-4)
  - GPUDirect RDMA有効 (nvidia-peermem)

## ベンチマーク方法

- **ツール**: llama-bench
- **繰り返し**: `-r 3` (3回測定)
- **テストパラメータ**: `-p 128 -n 32` (pp128, tg32)
- **レイヤー分割**: `-sm layer -ngl 999`

## 分析

### 1. リモートGPU数の影響

#### RDMA の場合

| リモート数 | tg32 影響 | 備考 |
|:----------:|:---------:|------|
| 1 | 安定 (29-59 t/s) | 逐次実行1回 |
| 2 | 不安定 (32-57 t/s) | 逐次実行2回 |
| 4 | **深刻な劣化** (0.6-26 t/s) | 逐次実行4回 |

**原因**: RDMAデバイスごとに逐次 `graph_compute` が実行される。4リモートGPU = 4回の逐次graph_compute/トークン。

#### RPC の場合

| リモート数 | tg32 影響 | 備考 |
|:----------:|:---------:|------|
| 1 | 50-55 t/s | 安定 |
| 2 | 52-55 t/s | 安定 |
| 4 | 44-48 t/s | 緩やかな低下 |

RPCは複数リモートGPUでも比較的安定。

### 2. ローカル/リモート比率の最適化

#### gpt-oss-20b での最適構成

| 比率 | 構成 | RDMA tg32 | RPC tg32 | 推奨 |
|:----:|:----:|:---------:|:--------:|:----:|
| ローカル優位 | 3+1 | **58.96** | 55.76 | RDMA |
| バランス | 2+2 | **57.55** | 52.03 | RDMA |
| リモート優位 | 1+4 | 0.57 | **47.61** | RPC |

**発見**: ローカルGPU ≥ リモートGPU のとき、RDMAが有利。

#### gpt-oss-120b での最適構成

| 比率 | 構成 | RDMA tg32 | RPC tg32 | 推奨 |
|:----:|:----:|:---------:|:--------:|:----:|
| ローカル多め | 6+2 | 32.53 | **38.58** | RPC |
| 最大構成 | 7+4 | 26.59 | **33.02** | RPC |

**発見**: 120bモデルでは全構成でRPCが安定。

### 3. pp128 (Prompt処理) の傾向

```
RPC: 全構成で 350-390 t/s の範囲で安定
RDMA: 構成によって 156-401 t/s と大きくばらつく
```

### 4. tg32 (トークン生成) の傾向

```
Best RDMA: 3+1 = 58.96 t/s (ローカル比92%)
Best RPC:  3+1 = 55.76 t/s (ローカル比87%)
```

## 結論

### GPU組み合わせの推奨

| シナリオ | 推奨構成 | 推奨バックエンド |
|---------|---------|----------------|
| 20bモデル、最高性能 | 3+1 または 2+2 | **RDMA** |
| 20bモデル、多GPU利用 | 4+4 | **RPC** |
| 120bモデル、全構成 | 6+2 または 7+4 | **RPC** |

### 重要な知見

1. **RDMAの最適条件**: ローカルGPU数 ≥ リモートGPU数
2. **リモート4GPU以上**: RPCを推奨 (RDMAの逐次実行オーバーヘッドが深刻)
3. **安定性**: RPCは全構成で標準偏差 < 2%、RDMAは構成依存で最大50%のばらつき
4. **120bモデル**: 現状RPCが全面的に有利

### スケーリング傾向

```
RDMA: GPU数増加に伴い性能が不安定化
      特にリモートGPU数が増えると著しく劣化

RPC:  GPU数増加に伴い緩やかに性能低下
      8GPU (4+4) でもpp128=355, tg32=45を維持
```

## 再現方法

### サーバー起動

```bash
# RDMA server (2号機)
ssh 192.168.100.2 "LD_LIBRARY_PATH=/home/ubuntu/projects/llama.cpp/build/bin \
  nohup /home/ubuntu/projects/llama.cpp/build/bin/rdma-server -H 0.0.0.0 -p 50051 > /tmp/rdma-server.log 2>&1 &"

# RPC server (2号機)
ssh 192.168.100.2 "LD_LIBRARY_PATH=/home/ubuntu/projects/llama.cpp/build/bin \
  nohup /home/ubuntu/projects/llama.cpp/build/bin/rpc-server -H 0.0.0.0 -p 50052 > /tmp/rpc-server.log 2>&1 &"
```

### ベンチマーク例 (2+2 GPU)

```bash
# RDMA 2+2
GGML_RDMA_SERVERS=192.168.100.2:50051 CUDA_VISIBLE_DEVICES=0,1 \
  build/bin/llama-bench \
  -m /home/ubuntu/.cache/llama.cpp/unsloth_gpt-oss-20b-GGUF_gpt-oss-20b-Q4_K_M.gguf \
  -dev 'CUDA0/CUDA1/RDMA0[192.168.100.2:50051]/RDMA1[192.168.100.2:50051]' \
  -ngl 999 -sm layer -r 3 -p 128 -n 32

# RPC 2+2
CUDA_VISIBLE_DEVICES=0,1 build/bin/llama-bench \
  -m /home/ubuntu/.cache/llama.cpp/unsloth_gpt-oss-20b-GGUF_gpt-oss-20b-Q4_K_M.gguf \
  --rpc 192.168.100.2:50052 \
  -dev 'CUDA0/CUDA1/RPC0/RPC1' \
  -ngl 999 -sm layer -r 3 -p 128 -n 32
```
